# 节点写作风格的自治——从硬编码模板到树内元节点

## 已知前提

- 当前 CLAUDE.md 硬编码了节点正文四段结构：「已知前提 → 认知起点 → 推导逻辑 → 讨论共识」
- `dt add` 默认生成这四段空模板（节点 012 的决策）
- 模型（Agent）读取 CLAUDE.md 后，无论什么类型的节点都用同一套骨架写
- 实际使用中，不同类型的讨论有完全不同的最佳表达方式：
  - 技术方案比较：需要对比表、pros/cons
  - 用户需求澄清：需要问答记录、修正历史
  - 项目目标定义：需要 why/what/boundary
  - 代码设计：需要接口定义、数据流
- 用户观察到：硬编码模板**反而约束了模型的上下文表达能力**

## 认知起点

核心问题：**如何让模型知道"这种节点应该怎么写"，但不是通过 CLAUDE.md 硬编码一套模板？**

用户提出的方向：把写作风格本身放进决策树里，作为一个"元节点"。模型看树的时候自然能看到这个风格指南，而且每个项目可以有自己的风格进化。

边界：
- 不是"去掉所有结构"——完全无结构的节点也没有价值
- 是"结构可定义、可进化、可项目化"
- CLAUDE.md 只需要说"看树里的写作风格节点"，而不是自己定义模板

## 推导逻辑

### 当前架构的问题

```
CLAUDE.md 写死模板 → 模型生成节点 → 所有节点长一样
```

问题链：
1. **一刀切**：goal 节点和 evaluation 节点用同一个骨架，不合理
2. **不可进化**：用户想调整风格，要改 CLAUDE.md，改了影响所有项目
3. **模型被锁定**：模型明明能根据内容选择最佳结构，但被模板限制了
4. **跨项目无差异**：一个技术项目和一个商业规划项目，节点写法应该不同

### 新架构：写作风格作为树的一部分

**核心思路：** 每个 dt 项目初始化时，自带一个"写作风格"根节点（或特殊节点），下挂各类型的范例/指南。

```
📦 项目初始化后的树：

🌳 _style [meta] 节点写作风格指南
├── _style_subproblem [meta] subproblem 节点的写法
├── _style_goal [meta] goal 节点的写法
├── _style_solution [meta] solution 节点的写法
└── _style_evaluation [meta] evaluation 节点的写法
```

**模型的行为变化：**
- 会话开始时 `dt tree` 能看到这个风格节点
- 创建新节点时，先看对应类型的风格范例
- 如果项目中风格节点被修改过（用户自定义），模型用修改后的版本
- 如果没有风格节点，模型自由发挥（降级行为）

**CLAUDE.md 只需说：**
> 创建节点前，先查看树中是否有 `_style` 开头的元节点。如有，遵循其风格指引。如无，自行决定最合适的结构。

### 实现方式讨论

**选项 A：特殊根节点（`root: true, type: meta`）**
- 优点：和普通节点统一存储，`dt tree` 可见
- 缺点：会和业务树混在一起，增加视觉噪音

**选项 B：隐藏目录 `.dt/styles/`**
- 优点：不污染业务树
- 缺点：模型 `dt tree` 看不到，需要额外命令或约定去读

**选项 C：普通根节点但 `dt tree` 可折叠/隐藏**
- 优点：数据统一，展示可控
- 缺点：需要 tree 命令改造

**选项 D：`dt init` 时生成预制节点，用户可删可改**
- 预制内容作为范例节点存在，不是"配置"而是"活的知识"
- 模型看到的是节点内容，不是配置文件
- 如果用户觉得不合适，直接编辑或删掉，模型下次就看到新版本

### 关键设计决策点

1. 风格节点是**根节点**还是挂在某个业务节点下？
2. 风格节点的 type 是新增 `meta` 还是复用已有类型？
3. `dt init` 是否默认创建风格节点？（还是可选？）
4. 模型找不到风格节点时的降级行为是什么？

## 讨论共识

**已确认的决策：**

1. **风格节点是独立根节点**（`root: true`）
2. **节点类型为 `style`**（新增类型）
3. **id 格式为 `style-{类型名}`**：`style-question`, `style-document`, `style-decision`, `style-exploration`
4. **id 系统需要兼容非纯数字**（所有节点都可以使用非数字 id）
5. **`dt init` 默认生成四个预制风格节点**
6. **完全可修改**：用户/模型可以编辑、删除预制节点，也可自创新类型
7. **可跨项目引用**：引用其他项目的 style 节点作为写作参考
8. **模型找不到风格节点时降级**：自由发挥，不强制结构
9. **CLAUDE.md 精简**：去掉硬编码模板，只说"创建节点前参考 `style-{type}` 节点"
10. **故事线/叙事通过树的结构展示**，不需要独立节点类型

**预制四个类型（替代旧的 goal/subproblem/solution/evaluation）：**

| 类型 | 覆盖的活动 | 典型场景 |
|------|-----------|---------|
| `question` | 提出问题、定义边界 | "我要弄清楚什么" |
| `document` | 原始记录、事实存档 | "这个模块做了什么" |
| `decision` | 方案选择、权衡记录 | "选 A 因为…" |
| `exploration` | 开放探索、还没有结论 | "我在想…" |

**需要的代码变更：**
1. id 生成系统改造——支持非数字 id，数字自增与字符串 id 共存
2. `dt init` 增加风格节点创建逻辑（四个预制 style 节点）
3. `dt add` 的 type 预设列表更新：`question / document / decision / exploration / style`（替代旧类型，旧类型仍可用作自定义）
4. 预制四个风格节点的正文内容（范例/指南）
5. CLAUDE.md 中去掉「节点正文结构」四段模板，改为引导模型看 style 节点
6. 支持跨项目引用 style 节点
