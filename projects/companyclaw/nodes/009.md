# 权限实现方案：OS原生ACL+应用层Policy双重机制

## 已知前提

- 004 节点设计了 system/teams/tenants 三层目录结构
- 005 节点设计了 Policy 策略层（YAML 定义权限规则）
- 用户问：是否需要沙箱？如何实现不同文件夹的权限？

## 认知起点

**核心问题**：如何确保 tenant A 无法访问 tenant B 的文件？

## 推导逻辑

**三层权限实现机制对比**：

| 方案 | 实现成本 | 安全性 | 适用场景 | 推荐度 |
|------|---------|--------|---------|--------|
| **OS 原生 ACL** | 低 | 高（内核级） | 所有文件系统访问 | ✅ 核心 |
| **应用层 Policy** | 中 | 中（依赖代码） | 业务逻辑权限 | ✅ 补充 |
| **Docker 沙箱** | 高 | 很高（完全隔离） | 代码执行场景 | ⚠️ 按需 |
| **K8s 容器隔离** | 很高 | 很高 | 大规模多租户 | ❌ 过度 |

**方案一：OS 原生 ACL（推荐核心）**

```
Windows (NTFS ACL)：
icacls "D:\company-agent\tenants\alice" /grant "COMPANY\alice:RW"
icacls "D:\company-agent\system" /grant "COMPANY\employees:RX" /inheritance:d

Linux (chmod+rwx)：
chown -R alice:company /company-agent/tenants/alice
chmod 700 /company-agent/tenants/alice      # 仅本人可读写
chmod 755 /company-agent/system             # 所有人可读、执行
```

每个租户映射为一个系统用户：
- `COMPANY\alice` / `alice` (租户用户)
- `COMPANY\backend_team` / `backend-team` (团队组)
- `COMPANY\all_employees` / `company` (公司全员组)

**方案二：应用层 Policy（补充控制）**

Policy YAML 示例：
```yaml
# system/policies/tenant-isolation.yaml
- name: tenant_isolation
  rule: |
    user.workspace_path.startsWith(f"tenants/{user.id}/")
  allowed_paths:
    - "tenants/{user.id}/**"      # 本人 workspace 完全访问
    - "teams/{user.team}/**"      # 团队资源可读
    - "system/skills/**"          # system 级只读
  denied_paths:
    - "tenants/*/credentials/**"  # 禁止访问他人 credentials
    - "teams/*/policies/**"      # 禁止修改团队策略
  audit: true
```

**方案三：沙箱（按需）**

是否需要沙箱取决于 Agent 是否会**执行代码**：

| Agent 类型 | 执行代码 | 是否需要沙箱 |
|-----------|---------|-------------|
| 对话/问答 | ❌ | ❌ 不需要 |
| 文件操作 | ❌ | ❌ 不需要 |
| **代码编写** | ✅ | ✅ Docker 隔离 |
| **命令执行** | ✅ | ✅ Docker 隔离 |
| API 调用 | ⚠️ | ⚠️ 可选 |

沙箱实现（轻量级）：
```dockerfile
# sandbox.Dockerfile
FROM python:3.13-slim
# 网络隔离：无外部网络
# 文件系统：只读模板 + 临时读写层
# 资源限制：CPU/内存/cpu
```

**混合方案架构**：

```
┌─────────────────────────────────────────────┐
│           应用层 Policy 检查                  │
│   (YAML规则、覆盖策略、审计日志)              │
├─────────────────────────────────────────────┤
│           OS 级 ACL 权限                     │
│   (NTFS/chmod 用户组 硬隔离)                │
├─────────────────────────────────────────────┤
│         可信操作 (读文件、对话)               │
│         → 直接访问文件系统                    │
├─────────────────────────────────────────────┤
│        高风险操作 (代码执行)                  │
│         → Docker 沙箱隔离                    │
└─────────────────────────────────────────────┘
```

## 讨论共识

**推荐的权限实现方案**：

1. **核心隔离：OS 原生 ACL**
   - 每个租户 = 一个系统用户（Linux uid / Windows SID）
   - 目录权限：tenant 700（仅本人）、team 750（组内）、system 555（只读）
   - 优点：内核级安全，无需信任应用代码

2. **业务控制：应用层 Policy**
   - Policy YAML 定义细粒度规则（如覆盖策略、可见性）
   - 作为 ACL 的补充，处理跨层逻辑
   - 优点：灵活可配置，可审计

3. **沙箱：仅对代码执行场景**
   - 对话/问答/文件操作：不需要沙箱（ACL 足够）
   - 代码执行/命令执行：Docker 沙箱
   - 不需要 K8s，Docker 足够（30-50 人规模）

**不需要沙箱的场景**：
- Agent 读取文件、写入文件
- Agent 调用 API、搜索知识库
- Agent 发送消息（微信/飞书）

**需要沙箱的场景**：
- Agent 需要执行 Python/Shell 代码
- Agent 需要安装包、编译程序
- Agent 需要访问网络（隔离场景）
