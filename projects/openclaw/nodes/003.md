# 协议间的异同：统一的设计空间

## 已知前提

已确定需要强隔离层：调用方不感知协议差异，所有输出走统一格式。设计统一格式之前，必须先理解各家协议实际的结构——格式设计的边界由现实约束决定。

## 认知起点

把当前主流的四种 AI Provider 协议结构逐一展开，找出它们的公约数和本质差异，从而推导出「任何工程师都会想到的最小统一格式」。

## 推导逻辑

### 第一步：逐一展开各家协议

**OpenAI Chat Completions（流式）**
```
请求：{ model, messages: [{role, content}], stream: true, tools? }
流式事件：data: {"choices":[{"delta":{"content":"..."},"finish_reason":null}]}
          data: {"choices":[{"delta":{"tool_calls":[...]},"finish_reason":null}]}
          data: {"choices":[{"finish_reason":"stop","usage":{...}}]}
```

**Anthropic Messages（流式）**
```
请求：{ model, messages: [{role, content}], max_tokens, stream: true, tools? }
流式事件：{"type":"content_block_start","content_block":{"type":"text"}}
          {"type":"content_block_delta","delta":{"type":"text_delta","text":"..."}}
          {"type":"message_delta","delta":{"stop_reason":"end_turn","usage":{...}}}
```

**Google GenerativeAI（流式）**
```
请求：{ contents: [{role, parts:[{text}]}], tools? }
流式事件：{"candidates":[{"content":{"role":"model","parts":[{"text":"..."}]}}]}
          {"candidates":[{"finishReason":"STOP"}],"usageMetadata":{...}}
```

**AWS Bedrock Converse Stream**
```
请求：{ modelId, messages: [{role, content:[{text}]}], toolConfig? }
流式事件：{contentBlockDelta:{delta:{text:"..."}}}
          {messageStop:{stopReason:"end_turn"}}
          {metadata:{usage:{inputTokens,outputTokens}}}
```

---

### 第二步：识别公约数

| 能力 | OpenAI | Anthropic | Google | Bedrock |
|---|---|---|---|---|
| 多轮对话（角色） | `role: user/assistant` | `role: user/assistant` | `role: user/model` | `role: user/assistant` |
| 文本输出 | `delta.content` | `text_delta.text` | `parts[].text` | `delta.text` |
| 工具调用 | `delta.tool_calls[]` | `tool_use` block | `parts[].functionCall` | `toolUse` block |
| 停止原因 | `finish_reason` | `stop_reason` | `finishReason` | `stopReason` |
| Token 用量 | `usage.prompt_tokens/completion_tokens` | `usage.input_tokens/output_tokens` | `usageMetadata` | `usage.inputTokens/outputTokens` |

**公约数**：所有协议都有「消息角色、文本输出、工具调用、停止原因、Token 用量」这五个维度。字段命名不同，但语义相同。

---

### 第三步：推导最小统一格式

基于公约数，任何工程师都会推导出：

```typescript
type MinimalAssistantOutput = {
  role: "assistant";
  text: string;                    // 文本输出
  toolCalls?: ToolCall[];          // 工具调用（可选）
  stopReason: string;              // 停止原因
  usage: {
    inputTokens: number;
    outputTokens: number;
  };
}

type ToolCall = {
  id: string;
  name: string;
  arguments: Record<string, unknown>;
}
```

这个格式覆盖了所有公约数，字段命名与协议无关，结构简单，调用方容易消费。

## 讨论共识

各家协议在「消息角色、文本输出、工具调用、停止原因、Token 用量」这五个维度上是同构的，差异只在字段命名和事件结构上。

基于此推导出的最小统一格式：`{ role, text, toolCalls?, stopReason, usage }`

这是纯粹从协议分析得出的理论最小解。**下一步是拿实际代码中的格式和这个最小解对比**——如果代码里的格式比这个复杂，说明开发者在实际集成中遇到了这个最小解没有处理到的真实问题。那些差异，才是值得深入追问的地方。
