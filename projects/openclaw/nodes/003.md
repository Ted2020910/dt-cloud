# 协议间的异同：统一的设计空间

## 已知前提

上层代码不感知协议差异，因此系统里必然有统一化层。但在设计这个统一层之前，必须先搞清楚：**各协议之间，哪些是相同的，哪些是本质不同的？** 相同点是统一格式的基础，不同点则是适配器必须处理的内容。

## 认知起点

在 `src/config/types.models.ts` 中发现了 `MODEL_APIS` 常量，明确列出了系统支持的 9 种 API 协议族：

```typescript
const MODEL_APIS = [
  "openai-completions",       // OpenAI Chat Completions（旧格式）
  "openai-responses",         // OpenAI Responses API（新格式）
  "openai-codex-responses",   // Codex 专用路由
  "anthropic-messages",       // Anthropic Messages API
  "google-generative-ai",     // Google Gemini
  "github-copilot",           // GitHub Copilot 协议
  "bedrock-converse-stream",  // AWS Bedrock Converse 流式
  "ollama",                   // Ollama 本地
  "azure-openai-responses",   // Azure OpenAI
]
```

**关键观察**：设计者没有试图模糊或隐藏这些差异，而是**明确枚举**了所有协议族。这是一种「承认差异、在边界处隔离」的策略信号。

## 推导逻辑

对比这 9 种协议的实际 HTTP 结构，可以识别出两类：

**相同点（公约数）——可以统一的部分：**
| 维度 | 所有协议共同点 |
|------|------|
| 消息角色 | 都有 `user` / `assistant` 轮次概念 |
| 文本输出 | 都会输出文本内容 |
| 工具调用 | 主流协议都支持 function/tool call |
| 流式响应 | 都支持 SSE 或 WebSocket 流式输出 |
| Token 用量 | 都有输入/输出 token 计量 |

**不同点（本质差异）——适配器必须处理的部分：**
| 维度 | 差异示例 |
|------|------|
| 请求体结构 | Anthropic 用 `max_tokens`，OpenAI Responses 用 `max_output_tokens` |
| 流式事件格式 | Anthropic 用 `content_block_delta`，OpenAI 用 `response.output_item.delta` |
| 工具调用字段 | Anthropic 用 `input`，OpenAI 用 `arguments` |
| 推理内容表示 | Anthropic 用独立 `thinking` 块 + `thinking_budget`，OpenAI 用 `reasoning_effort` |
| 缓存控制 | Anthropic 有 `cache_control: ephemeral`，OpenAI 有 `store` 字段，格式完全不同 |

**线索**：相同点的粒度告诉我们，统一格式应该围绕「角色 + 内容块 + 用量」建模。差异全部可以在协议边界内部消化，不需要泄漏到统一格式外。

## 讨论共识

统一格式的**设计空间**已经确定：

- **可以统一的公约数**：消息角色、内容块（文本/工具调用/推理）、token 用量
- **必须隔离的差异**：各协议的请求体结构、流式事件解析、特殊字段处理

下一个问题：**代码里实际选择了什么数据结构来表达这个统一格式？** 它的字段设计是否覆盖了所有公约数，又是否避免了把协议差异泄漏出来？
