# 多协议API统一化：设计出发点

## 已知前提

OpenClaw 是一个支持 50+ 个模型 provider 的 AI 助手平台。`extensions/` 目录下存在 `anthropic`、`amazon-bedrock`、`google`、`alibaba`、`deepseek`、`openrouter` 等大量 provider 插件。

## 认知起点

一个核心观察：所有主流 AI 模型对外都是 **HTTP API**，但每家的调用方式和数据结构完全不同——

- OpenAI 有 Chat Completions API 和 Responses API 两种格式
- Anthropic 用 Messages API，请求和响应结构与 OpenAI 完全不同
- Google 用 GenerativeAI API，又是另一套
- AWS Bedrock 用 Converse Stream，走 AWS SDK

这带来一个核心设计问题：**如何让上层应用代码不需要为每种模型写不同的逻辑？**

## 推导逻辑

**线索一**：翻看 `extensions/` 目录，发现有 50+ 个 provider 插件，但 `src/agents/session-runtime.ts`、`src/agents/cli-runner.ts` 等上层代码里，完全没有 `if provider === 'anthropic'` 或 `if provider === 'openai'` 这样的条件分支。

**线索二**：上层代码中大量使用 `Model<Api>` 类型，但处理返回结果时总是直接操作 `AssistantMessage` 对象，不关心它来自哪个 provider。

这两条线索说明：**系统里必然存在某种统一化层，把所有协议的差异在某个地方全部消化掉**。找到这个层，就找到了整个底层设计的核心。

## 讨论共识

这是一个经典的「多协议适配」架构问题。OpenClaw 面临的挑战是：

> 支持 50+ 种 provider，每种都有不同的 API 协议，但上层应用代码应该对协议完全无感知。

下一个问题自然浮现：**这些协议之间，哪些是可以统一的，哪些是本质上不同的？** 只有弄清楚这个边界，才能判断统一层应该怎么设计。
