# 多协议API统一化：设计出发点

## 已知前提

需要构建一个支持多个 AI 模型 Provider 的系统。各家 Provider 对外都暴露 HTTP API，但每家的请求结构、响应格式、流式协议各不相同。Provider 的数量不是固定的，未来还会持续增加。

## 认知起点

一个系统需要同时支持 OpenAI、Anthropic、Google、AWS Bedrock 等多家 Provider。这些 Provider 的 API 协议完全不同。

**核心问题**：调用方（使用模型能力的业务代码）是否应该知道自己在和哪个 Provider 的哪种协议打交道？

## 推导逻辑

把所有可能的设计策略列出来，逐一分析：

**选项 A：无隔离——调用方直接处理各家协议**

每个功能模块自己写 OpenAI 的调用逻辑、自己写 Anthropic 的调用逻辑。

约束分析：
- 假设有 F 个功能、P 个 Provider，需要维护 F × P 份协议处理代码
- 新增一个 Provider，所有 F 个功能都要改
- 新增一个功能，要为所有 P 个 Provider 各写一次
- 复杂度随 Provider 数量线性增长，当 P 增长到 50 时完全失控

结论：**不可行**，复杂度无法控制。

---

**选项 B：弱隔离——统一发请求，但不统一响应解析**

封装一个统一的「发请求」函数，调用方不用自己处理 HTTP 细节，但拿到的响应还是各家原始格式，调用方需要自己判断「这是 OpenAI 响应还是 Anthropic 响应」再解析。

约束分析：
- 发请求的复杂度确实降低了
- 但响应解析的复杂度没有变，仍然是 F × P
- 只是把问题从请求端移到了响应端
- 调用方依然需要感知 Provider 差异

结论：**不解决根本问题**，只是换了个地方出现相同的问题。

---

**选项 C：强隔离——统一接口 + 统一输出格式**

调用方只和一个统一接口交互，传入「用哪个模型、说什么」，拿到的输出是统一格式，不论底层是哪个 Provider。所有协议差异被封装在适配层内部。

约束分析：
- 新增 Provider：只需写一个适配器，其他 F 个功能完全不感知
- 新增功能：只需对着统一接口开发，不需要考虑 P 个 Provider 的差异
- 复杂度从 O(F × P) 降到 O(F + P)
- 代价：需要设计一个足够通用的统一格式，覆盖所有 Provider 的输出能力

结论：**这是唯一可扩展的方案**。

## 讨论共识

调用方不应该感知协议差异。系统需要一个强隔离层，对上暴露统一接口和统一输出格式，对下适配各家协议。

这个结论成为后续所有设计的前提。下一个问题自然浮现：**这个统一输出格式应该长什么样？** 要回答这个问题，必须先把各家协议实际的输出结构摆出来看——格式设计的空间由现实约束决定。
