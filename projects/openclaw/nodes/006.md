# 完整调用链：拼图收网

## 已知前提

经过 002→005 的逐层追查：
- **002**：系统面临多协议统一化问题，策略是「承认差异、在边界处隔离」
- **003**：协议间的公约数是角色/内容块/用量，差异在请求结构和流式格式
- **004**：统一格式是 `AssistantMessage`，内容用 `ContentBlock` 三种类型覆盖所有差异
- **005**：`StreamFn` 是统一抽象边界，`provider-transport-stream.ts` 是调度枢纽，适配器各自内聚，插件通过 `wrapStreamFn` 注入

## 认知起点

现在需要把所有发现组装成一个完整的调用链，验证这套设计是否自洽：**一个用户请求进来，它究竟经过哪几层，最终产出 `AssistantMessage`？**

## 推导逻辑

追踪 `src/agents/pi-embedded-runner.ts` 中一次模型调用的完整路径：

**第一层：模型解析**
```
"anthropic/claude-sonnet-4-6" (字符串)
    ↓ model-selection.ts / pi-embedded-runner/model.ts
Model<"anthropic-messages"> {
  id: "claude-sonnet-4-6",
  api: "anthropic-messages",
  provider: "anthropic",
  baseUrl: "https://api.anthropic.com",
  ...
}
```
把模型字符串解析成完整的 `Model<Api>` 对象，**`api` 字段在这里确定**，后续所有路由依赖它。

**第二层：StreamFn 注册**
```
provider-stream.ts / registerProviderStreamForModel()
    ├─ 先查：插件有没有为这个 provider 提供 StreamFn？
    └─ 没有 → createTransportAwareStreamFnForModel() → 走内置适配器
```
决定「用哪个流处理函数」，注册到 pi-ai 的自定义 API 表中。

**第三层：适配器调度**
```
provider-transport-stream.ts / createSupportedTransportStreamFn()
    switch (model.api):
      "anthropic-messages" → createAnthropicMessagesTransportStreamFn()
      "openai-responses"   → createOpenAIResponsesTransportStreamFn()
      ...
```
根据 `model.api` 分发到具体适配器，**这是协议路由的唯一决策点**。

**第四层：协议适配**
```
anthropic-transport-stream.ts（以 Anthropic 为例）
    发送 HTTP 请求 → api.anthropic.com/v1/messages
    解析 SSE 流：
      content_block_start → 初始化 ContentBlock
      content_block_delta → 累积 text / thinking / tool_input
      message_delta       → 填充 stopReason / usage
    输出 AssistantMessage ← 协议差异全部在这里消化
```

**第五层：统一消费**
```
pi-embedded-subscribe.ts / session-runtime.ts
    接收 AssistantMessage
    // 不需要知道来自哪个协议
    // 直接处理 content: ContentBlock[]
    // 直接读取 usage.input / usage.output
```

## 讨论共识

**完整调用链的五层结构：**

```
用户请求
    │
    ▼ ① 模型解析层（model-selection / pi-embedded-runner/model）
    │  字符串 → Model<Api>，确定 api 字段
    │
    ▼ ② StreamFn 注册层（provider-stream）
    │  插件 StreamFn 优先，否则走内置适配器
    │
    ▼ ③ 适配器调度层（provider-transport-stream）
    │  switch(model.api) → 分发到具体适配器
    │
╔═══════════════════════════╗
║  StreamFn 抽象边界         ║ ← 协议无关 / 协议有关 的分界线
╚═══════════════════════════╝
    │
    ▼ ④ 协议适配层（anthropic / openai transport stream）
    │  原生 HTTP 请求 + 流式解析 → MutableAssistantOutput → AssistantMessage
    │
    ▼ ⑤ 统一消费层（session-runtime / channel 层）
       AssistantMessage，完全协议无关
```

**设计自洽性验证**：
- ✅ 上层代码（第⑤层）确实没有任何 `if provider === 'anthropic'` 分支
- ✅ 新增 provider 只需在第④层添加适配器，其他层不变
- ✅ `api` 字段在第①层确定后，贯穿②③④层，始终是路由依据
- ✅ `thinking` 块统一了 Anthropic 和 OpenAI 两种完全不同的推理输出格式

**侦探结论**：这套设计的核心是 `StreamFn` 这条抽象线。它不是偶然出现的工具函数，而是整个多协议统一化设计的**架构边界**——上方是协议无关的业务逻辑世界，下方是各协议原生实现的世界，两个世界通过这条线严格分隔。
