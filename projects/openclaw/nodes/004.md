# 基础架构 vs 实际代码：差异揭示了什么问题？

## 已知前提

从协议分析推导出的最小统一格式：

```typescript
type MinimalAssistantOutput = {
  role: "assistant";
  text: string;
  toolCalls?: ToolCall[];
  stopReason: string;
  usage: { inputTokens: number; outputTokens: number; }
}
```

这是理论上最简单的方案。如果实际代码比这个复杂，多出来的部分一定是为了解决某个真实问题。

## 认知起点

看代码中实际的统一格式定义（`AssistantMessage`），和最小解做逐字段对比，找出所有「超出预期」的部分，并追问每一处多出来的设计是为了解决什么问题。

## 推导逻辑

### 对比：最小解 vs 实际代码

**实际代码的 `AssistantMessage`：**

```typescript
type AssistantMessage = {
  role: "assistant";
  content: ContentBlock[];         // ← 不是 text: string，而是块数组
  stopReason: StopReason;
  api: string;                     // ← 多了：协议标识
  provider: string;                // ← 多了：Provider 标识
  model: string;                   // ← 多了：模型标识
  usage: {
    input: number;
    output: number;
    cacheRead: number;             // ← 多了：缓存读取 token
    cacheWrite: number;            // ← 多了：缓存写入 token
    totalTokens: number;
    cost: { ... };                 // ← 多了：费用字段
  };
  timestamp: number;
  responseId?: string;
  errorMessage?: string;
}

type ContentBlock =
  | { type: "text"; text: string }
  | { type: "thinking"; thinking: string; thinkingSignature: string; redacted?: boolean }
  | { type: "toolCall"; id: string; name: string; arguments: unknown }
```

---

### 逐差异追问

**差异一：`text: string` → `content: ContentBlock[]`**

最小解把文本和工具调用分成两个字段。但实际代码把它们放进了同一个数组。

为什么需要数组？模型的一次回复可以同时包含多个文本块和多个工具调用，而且它们之间有**顺序关系**——「先说了一段话，调用了工具A，又说了一段话，再调用工具B」。用 `text` + `toolCalls[]` 两个字段，这个顺序信息就丢失了。

**这揭示了最小解没有考虑到的问题**：模型输出是**交错排列的内容流**，不是「一段文本 + 若干工具调用」的简单结构。

---

**差异二：`ContentBlock` 里出现了 `thinking` 类型**

最小解里完全没有 `thinking`。但实际代码里它是第三种 ContentBlock，还带有 `thinkingSignature` 和 `redacted` 字段。

为什么需要 `thinking` 块？2024 年后，Claude 3.7+、OpenAI o1/o3 等模型开始输出推理过程。这既不是「最终回复文本」，也不是「工具调用」，是第三种输出类型。

`thinkingSignature` 和 `redacted` 又是为什么？这说明 `thinking` 不只是普通文本——它有来源校验和安全处理，暗示跨模型切换时还有额外的复杂性。**这个问题值得单独追问。**

---

**差异三：`api`、`provider`、`model` 三个标识字段**

统一格式的目的是让调用方不感知协议差异，为什么还要把协议信息存进去？

不是为了让调用方做条件分支，而是为了**多轮对话中切换模型**的场景。当对话历史里混有来自不同模型的消息，下一轮需要把历史发回给新模型时，系统需要知道每条历史消息的来源——因为有些内容（如 `thinkingSignature`）只有原始模型能验证，切换模型后必须特殊处理。

---

**差异四：`usage` 里多了 `cacheRead`、`cacheWrite`、`cost`**

最小解的 `usage` 只有 `inputTokens` 和 `outputTokens`。

Anthropic 和 OpenAI 都引入了 Prompt Cache 机制：缓存命中的 token 价格比普通 token 低 80%～90%。如果不区分缓存和非缓存 token，就无法准确计算每次请求的实际费用。

---

### 整理：差异揭示的四个真实问题

| 差异 | 背后的真实问题 |
|---|---|
| 数组而非独立字段 | 模型输出是交错内容流，顺序不能丢失 |
| `thinking` 块 | 现代模型出现了第三种输出类型：推理过程 |
| 协议标识字段 | 多轮对话切换模型时，历史消息的来源信息不能丢 |
| 缓存 token 计量 | Prompt Cache 让 token 有了不同的价格，简单计数无法反映真实成本 |

## 讨论共识

第一轮螺旋完成。最小统一格式和实际代码的对比，暴露了四个最小解未能覆盖的真实问题。

其中**「thinking 块」**是最值得深入追问的——它不只是新增一个字段，而是暗示「模型输出的类型系统」本身比最小解预设的更复杂，而且 `thinkingSignature` 和 `redacted` 的存在说明不同 Provider 之间的 thinking 实现有本质差异。

**第二轮螺旋的起点**：现代模型输出了推理过程，但各家的实现方式完全不同——Anthropic 的 thinking 块带有签名，OpenAI 的 reasoning 是独立字段，格式不兼容。统一格式如何处理这种新的输出类型，并且在跨模型切换时保持一致性？
