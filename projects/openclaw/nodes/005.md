# 差异的隔离点：适配器层的形状

## 已知前提

统一格式 `AssistantMessage` 已经确定。所有协议的原始输出（各自不同的流式事件格式）最终都要翻译成这个格式。现在需要找到：翻译工作由谁来做，边界划在哪里。

## 认知起点

`src/agents/provider-stream.ts` 中有一个函数 `registerProviderStreamForModel`，它的返回值类型是 `StreamFn`——这个类型来自 `@mariozechner/pi-agent-core`。**`StreamFn` 就是翻译层的统一接口抽象**。所有协议适配器，不管内部实现多复杂，对外暴露的都是同一个 `StreamFn` 签名。

## 推导逻辑

**线索一：`provider-transport-stream.ts` 是调度枢纽**

```typescript
// src/agents/provider-transport-stream.ts
function createSupportedTransportStreamFn(model: Model<Api>): StreamFn | undefined {
  switch (model.api) {
    case "openai-responses":
    case "openai-codex-responses":
      return createOpenAIResponsesTransportStreamFn();     // → openai-transport-stream.ts
    case "openai-completions":
      return createOpenAICompletionsTransportStreamFn();   // → openai-transport-stream.ts
    case "azure-openai-responses":
      return createAzureOpenAIResponsesTransportStreamFn(); // → openai-transport-stream.ts
    case "anthropic-messages":
      return createAnthropicMessagesTransportStreamFn();   // → anthropic-transport-stream.ts
    case "google-generative-ai":
      return createProviderOwnedGoogleTransportStreamFn(); // → 插件提供
  }
}
```

根据 `model.api` 字段分发——**api 字段是协议路由的唯一依据**。

**线索二：每种 API 族有独立适配器文件**

```
src/agents/
├── anthropic-transport-stream.ts   ← 解析 Anthropic SSE 流，输出 AssistantMessage
├── openai-transport-stream.ts      ← 解析 OpenAI Responses/Completions/Azure 流
├── transport-stream-shared.ts      ← 通用工具（流的 push/end/fail 操作）
└── transport-message-transform.ts  ← 跨模型消息历史归一化（切换模型时处理历史记录）
```

每个适配器内部持有一个 `MutableAssistantOutput` 临时对象，随着流式事件推进逐步填充，最终 `finalize` 时输出完整的 `AssistantMessage`。

**线索三：插件通过 `wrapStreamFn` 注入自定义逻辑**

`ProviderPlugin` 类型中有一个钩子：

```typescript
type ProviderPlugin = {
  wrapStreamFn?: (ctx: ProviderWrapStreamFnContext) => StreamFn | null | undefined;
  // ...
}
```

`registerProviderStreamForModel` 的逻辑是：**先查插件提供的 StreamFn，找不到再走内置适配器**。这意味着第三方 provider 插件可以完全接管流处理逻辑，同时仍然保持对上层代码透明——因为输出的还是同一个 `AssistantMessage` 格式。

**设计决策的反推**：为什么选择「分散的小适配器 + 统一接口」，而不是「一个中央转换函数」？

- 新增 provider 只需新增一个适配器文件，不修改已有代码（开闭原则）
- 各协议的流解析逻辑各自内聚，互不影响
- 插件体系可以用同样的接口注册全新协议

## 讨论共识

翻译层的形状已经清晰：

```
StreamFn（来自 @mariozechner/pi-agent-core）
  ↑ 统一抽象边界，上方全部是协议无关代码
  │
  ├─ provider-transport-stream.ts（调度枢纽，按 model.api 分发）
  │   ├─ anthropic-transport-stream.ts（Anthropic 适配器）
  │   ├─ openai-transport-stream.ts（OpenAI/Azure 适配器）
  │   └─ 插件提供的 StreamFn（Google/Bedrock 等由 provider 插件实现）
  │
  └─ transport-stream-shared.ts（流操作公共工具）
```
